# AstroHealth — Intelligent Health Monitoring Beyond Earth

> **NASA Space Apps Challenge 2026 — Challenge 5:** *"Create Health Monitoring Software for Astronauts on Space Missions"*  
> **Project Type:** Independent Student Innovation Prototype  
> **Data & Medical Notice:** `SIMULATED DEMONSTRATION DATA — NOT REAL ASTRONAUT MEDICAL RECORDS.` AstroHealth is an independent educational prototype, not an official NASA product, and not a certified medical device. It does not diagnose medical conditions, prescribe treatment, or replace professional medical judgment.

---

## 1. Project Overview

**AstroHealth** is a full-stack aerospace mission-control health monitoring platform designed to demonstrate how astronauts and mission support teams can track longitudinal health records during orbital and deep-space missions.

The platform unifies:
- **Mission Health Overview (`Overview`):** Dynamic KPI statistics, interactive multi-astronaut heart-rate trends, sleep recovery progress, habitat radiation dosimetry summaries, and recent observations.
- **Crew Management & Individual Astronaut Profiles (`Astronauts`):** Selectable crew cards and comprehensive individual profile views for four demonstration crew members (`Alex Rivera`, `Sarah Chen`, `James Miller`, `Lisa Park`) aggregating their vitals, sleep history, wellbeing check-ins, and alerts.
- **Multi-Parameter Vital Signs Monitoring (`Vital Signs`):** Interactive charts and reading logs for Heart Rate (`BPM`), Blood Oxygen (`SpO2 %`), Systolic/Diastolic Blood Pressure (`mmHg`), Respiration Rate (`br/min`), and Skin Temperature (`°C`), plus manual crew entry logging.
- **Sleep & Circadian Monitoring (`Sleep Monitor`):** Stacked sleep architecture charts (`Deep`, `REM`, `Light` sleep hours), sleep efficiency metrics, astronaut filtering, and manual sleep logging.
- **Crew Wellbeing & Fatigue Check-ins (`Wellbeing`):** Non-diagnostic subjective self-reports tracking mood (`1–5`), perceived fatigue (`Low`, `Moderate`, `Elevated`), workload balance, and timestamped crew notes.
- **Space Environment Radiation Monitoring (`Radiation`):** Daily and cumulative mission dosimetry records (`mSv`), habitat location context, solar activity state, trend charts, and manual dosimeter logging.
- **Transparent AI Health Assistant (`AI Health Assistant`):** Deterministic, local rule-based analytical engine (`RULE_BASED_LOCAL`) that summarizes crew health records and answers interactive questions (`AI_DERIVED`) with clean server-side extensibility for future LLM providers.
- **NASA Open Science Data Repository Integration (`NASA Research`):** Live search integration with the public NASA OSDR API (`https://osdr.nasa.gov/osdr/data/search`) paired with a verified catalogue of real spaceflight studies (`OSD-53`, `OSD-943`, `OSD-343`, `OSD-87`, `OSD-174`) and official portals (`NASA OSDR`, `NASA HRP`, `NASA NLSP`).
- **Global Search, Notifications & Offline Support:** Instant cross-domain search modal, read/unread notification management, and `localStorage` caching with an offline synchronization queue for manual entries.

## 2. Strict Data Integrity & Classification Standard

Every record across the backend API and frontend UI displays an explicit source classification badge:

| Classification | Badge Color | Meaning in AstroHealth |
| :--- | :--- | :--- |
| **`SIMULATED`** | Amber | Pre-seeded fictional demonstration records for Mission `ORBITAL-01`. Never presented as real astronaut telemetry. |
| **`MANUAL`** | Green | Records entered interactively by a user via the Vital Signs, Sleep, Wellbeing, or Radiation forms. |
| **`NASA_RESEARCH`** | Cyan | Verified scientific studies and metadata from NASA OSDR, HRP, and NLSP. Never presented as live crew vital signs. |
| **`AI_DERIVED`** | Purple | Explainable observations and Q&A summaries generated by the local rule-based analytical assistant. |
| **`SENSOR`** | Teal | Reserved strictly for verified physical sensor hardware connections (not claimed in this simulation prototype). |

## 4. Installation & Running the Application

### Prerequisites
- **Node.js** (v18+ recommended) and `npm`
- **Python** (3.10+ recommended; virtual environment already included in `backend/venv`)

### Step 1: Start the Backend API (`http://127.0.0.1:8000`)
Open PowerShell in `C:\Users\lenovo\Desktop\AstroHealth\backend`:

```powershell
cd C:\Users\lenovo\Desktop\AstroHealth\backend
.\venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

> **Note:** If setting up on a fresh machine without `venv`, run:
> ```powershell
> python -m venv venv
> .\venv\Scripts\pip.exe install -r requirements.txt
> ```

- **Backend API Root:** http://127.0.0.1:8000/
- **Interactive Swagger UI (`/docs`):** http://127.0.0.1:8000/docs

### Step 2: Start the Frontend (`http://localhost:5173`)
Open a second PowerShell terminal in `C:\Users\lenovo\Desktop\AstroHealth\frontend`:

```powershell
cd C:\Users\lenovo\Desktop\AstroHealth\frontend
npm.cmd run dev
```

- **Local Application URL:** http://localhost:5173/

## 5. Environment & Database Configuration

Copy `.env.example` to `backend/.env` if you wish to connect to a local or remote **MySQL** database or customize environment settings:

- By default (`DB_ENGINE=sqlite`), AstroHealth automatically creates and seeds a local SQLite database (`backend/astrohealth_demo.db`) using the exact same SQLAlchemy ORM models so the application works immediately with zero external setup.
- When `DB_ENGINE=mysql` and `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_HOST` / `MYSQL_DATABASE` are provided in `backend/.env`, AstroHealth connects to MySQL via `pymysql` (and safely falls back to SQLite if the MySQL server is offline).
- Full setup instructions and table schemas are documented in [`documentation/DATABASE_SETUP.md`](documentation/DATABASE_SETUP.md).

## 6. REST API Endpoints Summary

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `GET` | `/` | API status, version, database mode, and UTC timestamp |
| `GET` | `/api/health` | Health check and active SQLAlchemy database status |
| `GET` | `/api/about` | Project identity, medical disclaimers, and supported classifications |
| `GET` | `/api/mission` | Mission `ORBITAL-01` metadata, duration, and progress |
| `GET` | `/api/astronauts` | List all crew members with aggregated vitals, sleep, and wellbeing metrics |
| `GET` | `/api/astronauts/{id}` | Detailed individual astronaut profile with full reading logs and alerts |
| `GET` | `/api/vitals` | Multi-parameter vital readings (supports `?astronaut_id=` filter) |
| `POST` | `/api/vitals` | Log a new manual vital sign reading (`MANUAL`) |
| `GET` | `/api/sleep` | Crew sleep duration and stage records (supports `?astronaut_id=` filter) |
| `POST` | `/api/sleep` | Log a new manual sleep session (`MANUAL`) |
| `GET` | `/api/wellbeing` | Subjective mood, fatigue, and workload check-ins |
| `POST` | `/api/wellbeing` | Submit a new manual wellbeing check-in (`MANUAL`) |
| `GET` | `/api/radiation` | Mission habitat radiation dosimetry records and cumulative exposure |
| `POST` | `/api/radiation` | Log a new manual radiation dosimetry entry (`MANUAL`) |
| `GET` | `/api/alerts` | System observations and notifications (supports `?priority=` & `?astronaut_id=`) |
| `PATCH` | `/api/alerts/{id}/read` | Toggle read/unread status of a notification |
| `POST` | `/api/alerts/mark-all-read` | Mark all notifications as read |
| `GET` | `/api/ai/summary` | Generate rule-based health observations (`AI_DERIVED`, supports `?astronaut_id=`) |
| `POST` | `/api/ai/ask` | Ask a natural-language question about recorded crew data (`AI_DERIVED`) |
| `GET` | `/api/nasa/research` | Query live NASA OSDR API + verified space-health study catalogue (`NASA_RESEARCH`) |
| `GET` | `/api/search?q=` | Unified global search across astronauts, vitals, wellbeing, alerts, and NASA studies |

## 7. Known Limitations

1. **Simulated Demonstration Crew Telemetry:** Because real astronaut health records are confidential medical data, all crew vital signs, sleep logs, wellbeing check-ins, and radiation entries are simulated (`SIMULATED`) or manually entered (`MANUAL`) for demonstration purposes.
2. **Non-Clinical Educational Prototype:** Reference ranges shown in charts are illustrative only. AstroHealth is not certified for clinical diagnosis or medical decision-making.
3. **Rule-Based AI Assistant by Default:** Out-of-the-box, the AI Health Assistant runs a deterministic local rule-based engine (`RULE_BASED_LOCAL`) so it works reliably without requiring paid third-party LLM API keys.
